# Stackwise dependency update, 15 October 2026

The indexed repository reported three affected manifest entries representing two
unique packages: Next.js 16.2.6 and cryptography 46.0.7. The Python package appeared
in both `pyproject.toml` and `requirements.txt`; advisory aliases can also refer to
the same underlying issue. Manifest entries and advisory identifiers are not a
count of distinct exploitable vulnerabilities.

This update pins Next.js and eslint-config-next to 16.4.1 and cryptography to
50.0.2. The JavaScript lockfile includes the corresponding Next.js native builds,
image dependency updates and ESLint dependencies. The pnpm workspace records only
exact-version release-age exceptions generated during this security update; it
does not disable release-age checks globally. The Python runtime constraint file
uses the same cryptography pin as both manifests.

Validation on Linux, Node 24.19.0 and Python 3.12:

- 51 Python tests and 10 UI tests passed.
- ESLint, TypeScript and the Next.js 16.4.1 production build passed.
- `pip check` found no broken requirements.
- A public synthetic Fernet token generated by cryptography 46.0.7 decrypts
  through Stackwise on cryptography 50.0.2 with the same key. Production secrets
  were not accessed. Existing encryption keys must be retained.

OSV lookup results for the upgraded versions are included in
`data/evaluation/stackwise_dependency_update_20261015.json`. They apply only to
the named exact direct versions at the recorded time, not all transitive
dependencies or every application feature.

After the update is pushed, verify Vercel reports Ready and the live Python
health endpoint still identifies Stackwise. Refresh the connected repository's
index in Workspaces before inspecting Dependencies again: saved snapshots and
previous reports deliberately retain their original evidence. Existing database
records, access credentials and historical evaluation are not migrated or erased
by this dependency update. Queue delivery, private GitHub access and all live
security boundaries are not proven by these local tests.
